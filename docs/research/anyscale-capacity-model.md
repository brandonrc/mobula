# Anyscale shared compute capacity model — deep dive for Mobula

Date: 2026-08-16. Sources: official Anyscale docs (docs.anyscale.com), anyscale.com, and corroborating third parties where flagged. Anything we could NOT verify is listed at the end of each section.

## 1. Compute config / instance types

An Anyscale **compute config** defines one cluster's shape: one head node config plus a list of named, heterogeneous worker node groups (CPU and GPU groups can coexist). It is a superset of the OSS Ray cluster YAML. — https://docs.anyscale.com/configuration/compute

Current YAML schema: `head_node: {instance_type, resources, ...}` and `worker_nodes: [{name, instance_type, min_nodes, max_nodes, market_type, resources, labels, required_resources, required_labels, advanced_instance_config, flags}]`, plus cluster-wide logical caps `min_resources`/`max_resources` (e.g. `max_resources: {CPU: 6, GPU: 10}` — the legacy flat `max_workers` is deprecated), `zones`, `enable_cross_zone_scaling`, `auto_select_worker_config`. — https://docs.anyscale.com/reference/cli/compute-config

Registered compute configs are **immutable and versioned** (`name:version`, IDs like `cpt_abc123`); edits create new versions. — https://docs.anyscale.com/configuration/compute/create

Per worker group, exactly one of:
- `instance_type` — a predefined cloud VM type (`m5.2xlarge`); on K8s, an admin-defined pod shape. — https://docs.anyscale.com/configuration/compute/declarative
- `required_resources` (declarative, beta) — `CPU`, `memory` (Gi/Mi), `GPU`, `TPU`, plus `required_labels` like `ray.io/accelerator-type: H100`. Anyscale filters candidate instance types (fuzzy CPU/memory up to 2×, exact GPU count/type), ranks by cost efficiency, and selects up to the **top 3 instance types per worker group** as internal "instance groups" sharing one min/max bound — lower-cost options launch first. — https://docs.anyscale.com/configuration/compute/declarative

Market type per worker group: `ON_DEMAND`, `SPOT`, or `PREFER_SPOT` (spot first, fall back to on-demand; if spot later returns, on-demand nodes are evicted and replaced). Internally a PREFER_SPOT group is split into `{name}/spot` and `{name}/on-demand` subgroups with a spot-preferred ranking. — https://docs.anyscale.com/reference/cli/compute-config , https://docs.anyscale.com/configuration/compute/advanced

**Fallback ordering** across worker groups: the `instance_ranking_strategy` flag supports `custom_group_order` (explicit ranked tiers, e.g. reserved → spot → on-demand; nested lists = equal tier) and `price` (beta, AWS). With `enable_replacement` + `replacement_threshold` (default 60 min spot recheck), nodes from lower-ranked groups are actively replaced by higher-ranked capacity; replacement signals Ray like a spot preemption. — https://docs.anyscale.com/configuration/compute/advanced

Mapping to Ray: each node group `name` is registered with Ray's `available_node_types`; per-group `resources` override Ray logical resources; default labels include `ray.io/node-group`, `ray.io/market-type`, `ray.io/accelerator-type`, zone/region. Head node scheduling is disabled by default on multi-node clusters. — https://docs.anyscale.com/archive/ref/compute-config-api , https://docs.anyscale.com/configuration/compute/advanced

*Not verified:* a user-authored ordered list of instance types **within** one worker group (docs only describe Anyscale auto-selecting up to 3 for declarative groups). The legacy YAML v1/v2 fields were removed Jan 29, 2026. — https://docs.anyscale.com/archive/ref/compute-config-api

## 2. Resource pools / instance pools / quotas

Anyscale's first-class pool concept above individual clusters is called a **machine pool** (beta) — not "resource pool" or "instance pool". It is a hybrid: a named, **fixed-size pool of provisioned machines** per machine type (option (a)-ish), primarily intended to wrap **cloud capacity reservations** (option (c)), shared across jobs, services, and workspaces. — https://docs.anyscale.com/machine-pools

- Pool spec (YAML + CLI): `kind: ANYSCALE_MANAGED` (Anyscale creates/terminates cloud instances) or `CUSTOMER_MANAGED` (register on-prem machines). Each pool has `machine_types`, each with `launch_templates` (cloud `instance_type`, `market_type`, zones, `advanced_instance_config`) and **partitions** — named groups with `size` (max machines) plus scheduling rules. Docs recommend setting partition `size` to the cloud-account quota for that machine type. — https://docs.anyscale.com/machine-pools/config-ref
- Cloud reservations are targeted per launch template, e.g. AWS `CapacityReservationSpecification.CapacityReservationTarget.CapacityReservationId` in `advanced_instance_config`. — https://docs.anyscale.com/machine-pools/config-ref
- Pools are org-level resources explicitly **attached to one or more Anyscale clouds** (`anyscale machine-pool attach --cloud ...`). Supported on VM-based AWS/GCP and Kubernetes-backed EKS/GKE clouds; not Azure/AKS; beta. — https://docs.anyscale.com/machine-pools
- Recycle policy (`max_workloads`, `rotation_interval`, `max_idle_duration`) rotates pool instances; on K8s, pods rotate after each workload. — https://docs.anyscale.com/machine-pools/config-ref

**Workload → pool assignment:** opt-in per worker group in the compute config — `instance_type` maps to the pool's `machine_type` name and a `flags.cloud_deployment.machine_pool: <name>` selects the pool; `instance_ranking_strategy` defines fallback across reserved → spot → on-demand machine types. — https://docs.anyscale.com/machine-pools

Separately, Anyscale has **resource quotas** (option (b)): org-admin-created limits scoped by cloud (required) + optionally project and/or user, one quota per cloud-project-user combination. Dimensions: max CPUs, max instances, max GPUs, max count per accelerator type. Hard limits pause scaling and raise "quota exceeded" on new launches (existing clusters keep running); soft limits only alert. Quotas never terminate clusters. — https://docs.anyscale.com/administration/resource-management/resource-quotas

*Not verified:* any feature literally named "resource pool"/"instance pool"; machine-pool GA date or pricing; a blog/talk announcing machine pools.

## 3. Elastic sharing and preemption

Two generations of cross-workload scheduling exist:

**Machine pools + Global Resource Scheduler (beta).** The GRS is a control-plane service that allocates machines from fixed-size pools to workloads, queues workloads FIFO when capacity is short (later workloads may bypass non-runnable earlier ones), and **preempts lower-priority workloads** by evicting machines; eviction notices name the preempting cloud/project/user/workload. — https://docs.anyscale.com/machine-pools/global-resource-scheduler

- Partitions carry ordered rules in Kubernetes label-selector syntax over labels (`workload-type` = job/service/workspace, `cloud`, `project`) plus custom tags; each rule sets an integer `priority` and optional `quota` (max machines for matching workloads; `quota: 0` blocks; first match wins; default priority 0). — https://docs.anyscale.com/machine-pools/tutorial
- Documented preemption flow: a `priority:high`-tagged job matched to priority 100 evicts machines from a lower-priority job; the preempted job re-enters the queue at the front of its priority class, retries acquiring `min_nodes` until `workload_recovering_timeout`, then terminates (with `max_retries`, re-queued at the end). — https://docs.anyscale.com/machine-pools/tutorial
- Documented example: reserve 25% of pool GPUs for dev while production can expand to 100% when dev is idle — **idle capacity reuse is done via partition quotas + priority, not a dynamic fair-share algorithm.** — https://docs.anyscale.com/machine-pools/global-resource-scheduler

**"Anyscale scheduler" (alpha, Kueue-modeled).** Org-scoped declarative config with `resource_flavors`, `resource_queues` (per-flavor `nominal_quota` per resource), and `scheduling_rules` routing workloads to queues with bounded integer priorities; queues ordered by priority then FIFO; one queue can pool capacity across clouds/clusters. Preemption is only **within** a queue and only when `preemption.within_resource_queue: lower_priority` is set (`never` default). Quotas are fixed; **no cross-queue borrowing/lending or cohort fair-sharing is documented** despite the Kueue framing. — https://docs.anyscale.com/admin/scheduler , https://docs.anyscale.com/admin/scheduler/config-reference

**Idle capacity reclamation:** workspaces auto-terminate after inactivity (default 120 min console / 30 min CLI); the autoscaler downscales idle workers (`idle_termination_seconds`); job-queue clusters shut down after `idle_timeout_s` once drained; machine pools recycle idle instances via `max_idle_duration`. — https://docs.anyscale.com/workspaces/manage , https://docs.anyscale.com/configuration/compute/advanced , https://docs.anyscale.com/jobs/queues

**On K8s:** Anyscale integrates with Kueue (beta) via the `kueue.x-k8s.io/queue-name` label, gang-scheduling `min_count` worker pods as one pod group; autoscaled pods remain independent queue units. Cross-workload fairness on K8s is delegated to Kueue itself. — https://docs.anyscale.com/clouds/kubernetes/kueue , https://docs.ray.io/en/latest/cluster/kubernetes/k8s-ecosystem/kueue.html

*Not verified:* any documented fair-sharing algorithm (DRF, weighted fair share, cohort borrowing) — only the marketing word "fairness"; cross-queue or cross-project preemption in the alpha scheduler.

## 4. Multi-cloud / multi-region

- An **"Anyscale cloud"** is a logical entity binding the control plane to resources in **one** AWS account, GCP project, or Kubernetes cluster; an org holds many clouds. Compute stacks: VMs on AWS/GCP; K8s on EKS, GKE, AKS, or any reachable cluster (Azure is K8s-only). BYOC: all data-plane resources live in the customer's cloud account. — https://docs.anyscale.com/clouds
- A beta feature (self-hosted, `cloud register` clouds only) lets one Anyscale cloud hold **multiple "cloud resource configurations"** spanning regions and providers. Each resource config is pinned to one `provider` + one `region`; multi-region/multi-cloud = adding more configs. — https://docs.anyscale.com/clouds/multi-cloud
- **A cluster is pinned to a single cloud resource at a time** — "The head node and all worker nodes for a cluster must deploy to the same cloud resource." Failover is expressed in the compute config by listing multiple `cloud_resource` entries; on capacity failure Anyscale retries the next resource. Selection strategy: `availability` (scored by historical launch success) or `input_order`; `cloud_resource_starting_timeout` default 15 min. **Fallback works only for jobs, not workspaces/services.** — https://docs.anyscale.com/clouds/multi-cloud
- **Reserved capacity:** AWS On-Demand Capacity Reservations via `CapacityReservationSpecification` and Capacity Blocks for ML via `MarketType: capacity-block` in worker-group `advanced_instance_config`. — https://docs.anyscale.com/configuration/compute/aws . GCP specific reservations via `reservationAffinity` `consumeReservationType: SPECIFIC_RESERVATION`; `zones` must exactly match the reservation's zone. — https://docs.anyscale.com/configuration/compute/gcp
- The alpha Anyscale scheduler can pool capacity across multiple clouds and clusters in one queue, falling back across reservations → spot → on-demand and across providers per quotas. — https://docs.anyscale.com/admin/scheduler

*Not verified:* any mention of AWS Savings Plans / GCP Committed Use Discounts (only third-party note that BYOC lets customers apply existing cloud credits/EDPs — https://aionx.co/ai-comparisons/anyscale-ai-review/); whether Anyscale-hosted serverless clouds span regions.

## 5. Usage attribution & metering

- Unit of accounting is the **Anyscale Credit (AC)**, billed usage-based with published per-hour AC rates per instance family (CPU 0.0135 AC/hr, T4 0.5682, L4 0.9542, A10G 1.3635, A100 4.9591). — https://www.anyscale.com/pricing
- ACs measure "processing capacity per hour," varying by machine type — i.e. a **time-integrated, instance-hour-derived** unit, not point-in-time allocation. Dashboards can display AC or USD (conversion depends on the org's contractual rate). — https://docs.anyscale.com/administration/billing/budgets , https://docs.vantage.sh/connecting_anyscale
- **Attribution dimensions:** the usage dashboard (org-owner-only, "real-time") breaks cost down by **cloud, project, user, instance type, and cluster**, over a UTC time range, with CSV download. — https://docs.anyscale.com/administration/billing/usage-dashboard . The Aggregated Instance Usage CLI/API exports usage filterable by cloud and project (documented for customer-hosted clouds). — https://docs.anyscale.com/reference/cli/aggregated-instance-usage . Third-party FinOps (Vantage) confirms usage rows carry `cloud_id, workspace_id, cloud_provider, instance_type, user_email, user_id`. — https://docs.vantage.sh/connecting_anyscale
- **Default system tags** are applied to all underlying cloud resources: `anyscale-cloud-id`, `anyscale-org-id`, `anyscale-project-name`, `anyscale-workload-name`, `anyscale-username` — explicitly for cost attribution in the customer's cloud account. **Custom tags** (max 20 per workload) propagate to AWS tags / GCP labels / K8s labels; recommended taxonomy includes `team`, `cost-center`. Tag-based attribution happens in the cloud provider's billing tools, not the Anyscale dashboard. — https://docs.anyscale.com/resources/custom-tags
- **Budgets are soft limits** (no enforcement, no termination), scoped org/cloud/project, daily or monthly, denominated in ACs, alerts at 100% via email/Slack/webhook. — https://docs.anyscale.com/administration/billing/budgets
- **Live utilization:** console Dashboard (scoped by cloud/project) shows live hardware utilization and links to Grafana; metrics carry `ProjectName`, `WorkloadType`, `WorkloadName` labels (e.g. `ray_node_cpu_utilization`). Usage dashboard numbers are explicitly **estimates** that "might differ from your final bill." — https://docs.anyscale.com/administration/resource-management/telescope-dashboard , https://docs.anyscale.com/administration/billing/usage-dashboard

*Not verified:* any use of the terms "chargeback"/"showback"; a feature named "cost explorer" (it's "usage dashboard"); the precise AC→GPU-hour formula; whether the usage API covers Anyscale-hosted clouds.

## 6. Anyscale on Kubernetes (BYOK)

- **Proprietary operator, not KubeRay:** "KubeRay is an open source Kubernetes operator. Anyscale provides a proprietary operator for Kubernetes." Dual-plane architecture: SaaS control plane posts instructions to the operator; "Kubernetes handles all resource provisioning." Installed via Helm (`anyscale/anyscale-operator`). One Anyscale node = one pod. Supported on EKS, GKE, AKS, CoreWeave, Nebius, Lambda, OKE, and generic/on-prem clusters. — https://docs.anyscale.com/get-started/what-is-ray , https://docs.anyscale.com/get-started/architecture , https://docs.anyscale.com/clouds/kubernetes
- **Strict three-layer scheduling:** Kubernetes places pods on machines; the operator translates compute configs into pod specs; Ray places tasks/actors on pods. "Ray can only distribute capacity the operator requested and Kubernetes granted." — https://docs.anyscale.com/clouds/kubernetes/scheduling
- On K8s, an "instance type" is an **admin-defined pod shape** in the Helm chart (`workloads.instanceTypes.additional`): CPU/memory/GPU, accelerators, nodeSelector, tolerations. Declarative compute configs (beta) bypass this, generating arbitrary pod shapes from `required_resources`. — https://docs.anyscale.com/clouds/kubernetes/configure-helm , https://docs.anyscale.com/configuration/compute/declarative
- **Kueue integration (beta):** users set the `kueue.x-k8s.io/queue-name` label in the compute config; Anyscale gang-schedules the `min_count` pods of a worker group as one pod group (`pod-group-name`, `pod-group-total-count`); autoscaled pods are independent queue units; limitation: only `min_count`, and all min-pod worker groups must share one queue. YuniKorn also documented. — https://docs.anyscale.com/administration/cloud-deployment/integrate-with-kueue
- **Quotas live at the Anyscale platform layer** (cloud + project + user scoped), not as Kubernetes `ResourceQuota` objects — though exhausted namespace quotas can leave pods Pending. — https://docs.anyscale.com/administration/resource-management/resource-quotas
- **Node pools are not managed by Anyscale** in K8s mode: placement is via nodeSelectors/tolerations or `advanced_instance_config` strategic-merge patches on pod specs; **Karpenter support** is an opt-in Helm flag (`workloads.enableKarpenterSupport`). Recommended: dedicated namespace per Anyscale cloud; vCluster if you lack cluster-admin. — https://docs.anyscale.com/clouds/kubernetes/configure-helm , https://docs.anyscale.com/clouds/kubernetes/generic

*Not verified:* whether the operator derives from KubeRay code; any use of native `ResourceQuota` by the operator; machine-pool behavior inside K8s clusters.

## Extra: Anyscale autoscaler vs OSS Ray autoscaler

- Anyscale Runtime (formerly RayTurbo) is a proprietary Ray with "intelligent autoscaling" as a headline feature; APIs identical to OSS Ray. — https://docs.anyscale.com/runtime
- Documented differentiators: (1) an **actor-pool autoscaler for Ray Data** that scales actors within the cluster so jobs start immediately without waiting for full node scale-up, handles node preemptions gracefully, and is on by default — https://docs.anyscale.com/runtime/data , https://docs.anyscale.com/rayturbo/rayturbo-data/ ; (2) **replica compaction** in RayTurbo Serve (consolidating fractionally utilized nodes) — https://docs.ray.io/en/latest/_collections/ray-overview/examples/entity-recognition-with-llms/README.html ; (3) **elastic training** in Anyscale Train surviving node preemptions with mid-epoch resumption — https://docs.anyscale.com/runtime .
- Marketing claim "up to 5.1x faster node autoscaling" vs open-source KubeRay (Ray Summit 2024) could **not be verified on a first-party anyscale.com page** (originals 404/redirect); corroborated only by partners/secondary sources. — https://www.astronomer.io/blog/unlocking-power-scalable-machine-learning-anyscale-astronomer/ , https://www.datanami.com/this-just-in/anyscale-unveils-new-products-and-enhances-unified-ai-platform-at-ray-summit-2024/
- **OSS has partially closed the gap:** autoscaler v2 (alpha since Ray 2.10, better observability and graceful idle-node draining) became the **default on KubeRay in Ray ≥ 2.47/2.48**; KubeRay exposes `upscalingMode` (Conservative/Default/Aggressive) and `idleTimeoutSeconds`. — https://docs.ray.io/en/latest/cluster/kubernetes/user-guides/configuring-autoscaling.html , https://ray-project.github.io/kuberay/reference/api/ . Open v2 correctness bugs remain (e.g. ray-project/ray#47578, v2 ignoring minReplicas).

## Extra: queueing when capacity is exhausted

**Anyscale does not fail fast — the default at every layer is "wait in a queue," with bounded waits for jobs/workspaces and unbounded waits at the Ray/K8s layers.**

- Jobs/workspaces have `workload_starting_timeout` (default 25 min): failure to acquire minimum resources in time **terminates the workload**. Running workloads that lose minimum resources (e.g. spot preemption) enter `RECOVERING`, bounded by `workload_recovering_timeout` (default 25 min). These timeouts do **not** apply to services. — https://docs.anyscale.com/configuration/compute/advanced
- Zonal retry: on capacity failure in a zone, Anyscale terminates nodes and retries in another zone (`zone_starting_timeout` default 10 min; opt-in `enable_cross_zone_scaling`). — https://docs.anyscale.com/configuration/compute/advanced
- Job states include `PENDING`/`AWAITING_CLUSTER_START` (v1) and `STARTING` (v2) — jobs wait for cluster capacity rather than failing. — https://docs.anyscale.com/reference/cli/job
- **Persistent job queues** run jobs sequentially on one shared cluster; the queue cluster auto-scales to queued capacity needs; ordering via `PRIORITY` (0 = highest, ties by arrival), `FIFO`, or `LIFO`. Anyscale "doesn't schedule jobs to the persistent cluster until required capacity is available." — https://docs.anyscale.com/jobs/queues
- Capacity is often avoided before queueing via fallbacks: PREFER_SPOT → on-demand; up to 3 instance types per declarative group; machine-pool reserved → spot → on-demand ranking. — https://docs.anyscale.com/configuration/compute/advanced , https://docs.anyscale.com/configuration/compute/declarative
- Ray layer (inherited): infeasible task/actor requests and placement groups **stay pending indefinitely** (no fail-fast); the autoscaler launches nodes to satisfy the queue (`upscaling_speed` caps pending launches). On K8s, unplaceable pods stay `Pending`. — https://docs.ray.io/en/latest/ray-core/scheduling/placement-group.html , https://docs.anyscale.com/clouds/kubernetes/scheduling
- Services: on spot preemption Anyscale spins up on-demand replicas on the 2-minute cloud warning with "little to no downtime"; overload is rejected with HTTP 503 at `max_ongoing_requests`; rollouts can be resource-capped with `--max-surge-percent`. — https://docs.anyscale.com/services/scale , https://docs.anyscale.com/services/update

*Not verified:* whether a service rollout that can't acquire nodes ever fails (timeouts explicitly don't apply); explicit retry/backoff parameters exposed in Anyscale compute configs.

## What Mobula should copy

1. **Adopt the compute-config shape 1:1 as Mobula's per-cluster capacity spec** — named worker groups with `min_nodes`/`max_nodes`, one `instance_type` (or K8s pod shape) per group, `market_type: ON_DEMAND | SPOT | PREFER_SPOT` with automatic spot→on-demand fallback, and a cluster-wide `max_resources` cap. Version configs immutably (`name:version`) so launches are reproducible. This maps directly onto KubeRay `workerGroupSpecs` + Ray `available_node_types`, so the translation layer is thin.
2. **Implement "machine pools" as K8s-native warm pools, not a VM concept** — a CRD that pre-provisions a fixed-size set of Ray worker pods (or nodes via Karpenter/cluster-autoscaler node pools) per machine type, with `partitions` = {size, priority, quota} rules selected by labels (workload-type, project, custom tags). Anyscale's selector-based partition rules are a proven, copyable UX; on K8s the equivalent is largely expressible through Kueue `ClusterQueue` + `Cohort` + priority classes.
3. **Use real fair-sharing, not just fixed quotas.** Anyscale's documented model is fixed quotas + integer priorities + within-queue preemption only — no cross-queue borrowing (their Kueue-modeled scheduler notably omits cohort lending). Since Mobula builds on Kueue, it gets `Cohort` borrowing/lending for free; this is a place to be *better* than Anyscale, not just at parity.
4. **Copy the quota model:** hard/soft quotas scoped by (cloud/cluster, project, user) on dimensions {CPU, GPU, instances, per-accelerator counts}; hard = block new launches/scale-up without killing running work, soft = alert only. Never terminate running clusters on quota breach — Anyscale explicitly avoids this, and it's the right call for trust.
5. **Copy the exhaustion UX:** jobs queue (priority, then FIFO) with a bounded `workload_starting_timeout` (~25 min default) that terminates the job; running jobs that lose minimum resources get a bounded `RECOVERING` window with re-queue semantics; services never time out and instead surge on-demand replicas on spot-preemption warnings. Don't fail fast anywhere.
6. **Copy the fallback/ranking ladder:** per-workload ordered preference tiers (reserved → spot → on-demand) with an active **node replacement** loop that demotes nodes back down the ladder when preferred capacity returns (Anyscale's `replacement_threshold`, default 60 min), signaling Ray like a spot preemption. Kueue/Karpenter disruption mechanisms give the primitives; the policy is the differentiator.
7. **Meter time-integrated instance-hours attributed to (project, user, workload, cluster) and propagate labels all the way down** — Anyscale's system tags on every cloud resource (`project-name`, `workload-name`, `username`) plus custom tag propagation to cloud billing is their entire attribution story. On K8s this is: enforce label propagation (RayCluster → pods → nodes) and derive GPU-hours from pod lifetime × request, exported per project/user with CSV/API. Keep budgets soft (alerts at 100%), and label in-console numbers as estimates.
8. **Keep clusters pinned to one cloud/region; express multi-cloud as ordered failover for jobs only.** Anyscale's multi-resource cloud (resource configs pinned to provider+region, single-resource cluster placement, `availability`-scored or `input_order` fallback with a starting timeout, jobs only) is a simple, honest model that avoids cross-region scheduler complexity. Mobula can map this to a list of Kueue ClusterQueues across K8s clusters with admission fallback.

### Caveats / gaps in this report
- Several Anyscale features cited are **beta or alpha** (machine pools, GRS, declarative configs, multi-resource clouds, the Anyscale scheduler, Kueue integration) — semantics may change.
- No first-party confirmation of the "5.1x faster autoscaling" marketing number.
- Machine pools are not available on Azure/AKS; the alpha scheduler's cross-queue behavior is undocumented beyond fixed quotas.
- No Anyscale source found for chargeback/showback terminology, Savings Plans/CUDs, or fair-sharing algorithms — treat these as absent, not hidden.
